# FR groom — idea FR 검증

`idea` 상태 FR 을 사용자와 검증해 `validated`·`parked`·`dropped` 로 정리하거나 `idea` 로 둡니다. 사용자가 명시적으로 요청할 때만 수행합니다(`fr` skill 「모델 자기호출 경계」).

## 판정 기준

판정 기준은 이 표 한 곳에만 둡니다. `/fr do` 등 다른 절차는 이 표를 다시 적지 않고 이 skill 을 부릅니다.

| 결론 | 조건 | 반영 |
| --- | --- | --- |
| `validated` | 문제가 실제로 있습니다(재현·관측·코드 근거). 범위를 말할 수 있습니다. 지금 착수해도 막히는 것이 없습니다 | `/fr status <slug> validated` 절차 |
| `parked` | 문제는 있지만 지금 착수할 수 없습니다(선행 작업·외부 결정·더 모아야 할 관측). 다시 볼 조건을 한 문장으로 말할 수 있습니다 | `/fr park <slug>` 절차 |
| `dropped` | 문제가 없습니다. 또는 이미 해결됐거나, 다른 FR·작업과 겹치거나, 드는 비용에 비해 얻는 것이 없습니다 | `/fr status <slug> dropped` 절차 |
| `idea` 유지 | 결론이 나지 않았습니다. 사용자가 판단을 미뤘거나 확인할 정보가 지금 없습니다 | 상태를 바꾸지 않습니다 |

## 절차

### 1. 대상 정하기

- 인자가 없으면 `rd-workflow-workspace/backlog/FUTURE_REQUESTS.md` 활성 인덱스에서 상태가 `idea` 인 행을 인덱스 순서대로 고릅니다.
- 인자가 있으면 지정한 slug 를 그 순서대로 씁니다. 활성 인덱스에 없는 slug 는 「찾을 수 없음」, 상태가 `idea` 가 아닌 slug 는 「idea 아님 (현재: {status})」 으로 결과 요약표에 남기고 대상에서 뺍니다.
- 대상이 0건이면 끝냅니다. 인자가 없었으면 「groom 할 idea FR 이 없습니다」 를 보입니다. 인자로 지정한 slug 가 모두 빠졌으면 7단계 결과 요약표에 slug 마다 빠진 사유(「찾을 수 없음」 또는 「idea 아님 (현재: {status})」)를 보입니다.
- 근거를 읽기 전에 「groom 대상 {n}건: <slug 목록> — 근거를 읽은 뒤 판정 권장표를 보입니다」 를 한 줄로 보입니다. 대상이 많아 조사가 길어지면 FR 을 하나 끝낼 때마다 「{k}/{n} {slug} 조사 끝」 을 보입니다.

### 2. 근거 읽기 (대상 전부, 이 턴 안에서)

대상 FR 마다 아래를 읽습니다. 상세 설명을 사실로 받지 않고 코드·git·문서로 확인합니다. 코드·git·문서를 읽어 답할 수 있는 것은 사용자에게 묻지 않습니다.

- 상세 파일(`items/*.md`) 전체. 이전 `## groom 기록` 이 있으면 그 문답에서 이어 갑니다.
- `bash rd-workflow/scripts/check_fr_related_files_existence.sh <상세 파일>` — related files 가 아직 있는지.
- `bash rd-workflow/scripts/fr_related_history.sh <상세 파일>` — 등록 뒤 related files 를 바꾼 커밋. 커밋이 있으면 그 커밋이 이미 문제를 해결했는지 코드를 열어 확인합니다.
- 상세의 `depends-on`·`relates` 에 적힌 FR 의 상태.

FR 마다 상세 파일의 `git hash-object <상세 파일>` 값, 인덱스 행, 권장의 근거로 쓴 `depends-on`·`relates` FR 의 상태를 기억해 둡니다(4단계 재확인용).

FR 마다 다음 다섯 가지를 판단합니다: 문제가 지금도 실제로 있는가 / 왜 필요한가 / 범위가 어디까지인가 / 이미 해결됐거나 다른 FR 과 겹치는가 / 지금 착수를 막는 것이 있는가.

### 3. 판정 권장표

대상 전부를 한 표로 보입니다.

| # | FR | 권장 판정 | 근거 | 범위 수정 | 사람이 정할 것 |
| --- | --- | --- | --- | --- | --- |
| 1 | `<slug>` | validated / parked / dropped / idea 유지 | 확인한 파일·커밋·수치 한두 문장 | `request seed` 를 바꿀 내용, 없으면 `-` | 근거로 정해지지 않은 질문과 권장 답, 없으면 `-` |

- `parked` 를 권장하면 다시 볼 조건 문장을 근거 칸에 함께 적습니다.
- 표는 응답 본문에 냅니다. 답은 표를 낸 뒤 AskUserQuestion 질문 창으로 받습니다. 질문 창은 답할 때까지 화면 아래에 남아서, `/fr do` 호출 세션의 줄기 감시 알림이 질문을 밀어 올리지 않습니다. 질문 창에는 표를 다시 넣지 않습니다.

**번호 코드**는 질문 창의 「Other」 칸과 문장 답에서 함께 씁니다. `N` 은 권장표의 `#` 칸입니다. 여러 개는 쉼표로 잇고, 적지 않은 행은 권장대로 반영합니다.

```
1 전부 권장대로 · 0 중단 · Nv validated · Np <다시 볼 조건> parked · Nd dropped · Ni idea 유지 · Ns 건너뛰기 · N? 따로 문답
예: 2v, 3p 선행 FR 이 끝난 뒤, 5?
```

질문 창 (첫 질문):

- 질문 문구: 「판정 권장표에 어떻게 답합니까? Other 에 번호 코드를 칠 수 있습니다 — 」 뒤에 위 코드 블록의 첫 줄을 붙입니다.
- 선택지 네 개:
  - 「전부 권장대로 (Recommended)」
  - 「행별로 바꾸기」 — 두 번째 질문 창으로 번호 코드를 받습니다.
  - 「한 행만 따로 문답」 — 선택지 설명에 「나머지 행은 권장대로 먼저 반영합니다. 나머지도 바꾸려면 Other 에 번호 코드를 치십시오」 를 적습니다. 대상이 1건이면 그 행입니다. 2건 이상이면 두 번째 질문 창으로 행을 고릅니다. 선택지는 권장표의 행이고(4행 넘으면 앞 4행, 나머지는 Other 에 행 번호), 고른 행은 「개별 문답」 절로 다루며 나머지 행은 권장대로 반영합니다.
  - 「중단」
- 두 번째 질문 창(행별로 바꾸기): 질문 문구에 코드 블록 두 줄을 넣고 「Other 에 번호 코드를 치십시오」 라고 적습니다. 선택지는 「첫 질문으로 돌아가기」·「중단」 두 개입니다. 「첫 질문으로 돌아가기」 는 아무 행도 반영하지 않고 첫 질문 창을 다시 띄웁니다.

질문 창을 쓸 수 없으면(AskUserQuestion 도구가 없는 실행) 표 아래에 코드 블록을 보이고 「번호 코드나 문장(「전부 권장대로」 등)으로 답하십시오」 를 적은 뒤 턴을 끝내고 답을 기다립니다.

### 4. 답 반영

사용자 답을 행마다 적용합니다.

- **답 해석**: 답을 먼저 끝까지 해석하고, 그다음에 반영합니다. 질문 창의 선택지는 그대로 읽고, 「Other」 칸과 문장 답은 아래 규칙으로 읽습니다.
  - 번호 답은 쉼표로 나눈 토큰입니다. 글자는 대소문자를 가리지 않고, 숫자와 글자 사이 공백을 허용합니다. `p` 뒤 조건은 쉼표 뒤에 번호 토큰이 나오기 직전까지라서 조건 안에 쉼표를 써도 됩니다. 쉼표 뒤 조각이 코드 모양이면 번호 토큰으로 보고 조건을 끝냅니다. 코드 모양은 숫자만 있는 조각, 숫자 뒤에 글자나 `?` 하나만 있는 조각, `<숫자>p` 뒤에 공백과 조건이 오는 조각입니다. 번호 토큰은 아래 실패 검사를 그대로 받습니다(`5x`·`5` 는 해석 실패입니다). 그 밖의 조각(`2.0 릴리스가 나간 뒤` 등)은 조건에 붙습니다. 그래서 `3p 선행 FR 이 끝난 뒤, 5?` 의 `5?` 는 따로 문답이고, `3p 선행 FR 이 끝난 뒤, 0` 의 `0` 은 다른 토큰과 섞인 `0` 이라 해석 실패입니다.
  - `1` 과 행별 토큰을 함께 쓰면 행별 토큰을 적용하고 나머지 행은 권장대로 반영합니다.
  - 문장 답도 그대로 받습니다: 「전부 권장대로」, 「N번 <판정>」(`parked` 는 「N번 parked: <다시 볼 조건>」 이고, 조건이 없으면 아래 `parked` 조건 규칙을 따릅니다. 번호 코드 `Np` 도 같습니다), 「N번 따로」, 「N번 건너뛰기」, 「중단」. 문장 답에서도 적지 않은 행은 권장대로 반영합니다.
  - 아래 중 하나라도 있으면 해석 실패입니다: 표에 없는 행 번호, 위 여섯 글자 밖의 글자, `0`·`1` 이 아닌 글자 없는 숫자, 한 행에 서로 다른 두 답, 다른 토큰과 함께 쓴 `0`, 번호 답으로도 문장 답으로도 읽히지 않는 부분.
  - 해석에 실패하면 아무 행도 기록·상태 변경하지 않습니다. 3단계 두 번째 질문 창으로 다시 묻고, 질문 문구 앞에 「못 읽은 부분: <토큰들>」 을 붙입니다(질문 창이 없으면 같은 내용과 코드 블록을 응답에 보입니다). 다음 답은 처음 답처럼 전부 다시 해석합니다.
- **반영 전 재확인**: 행을 기록하기 직전에 그 FR 의 활성 인덱스 행, 상세 파일의 `git hash-object` 값, 권장의 근거로 쓴 선행·관련 FR 의 상태를 2단계에서 기억한 값과 비교합니다. 하나라도 다르거나 행이 없으면 그 행은 기록·상태 변경 없이 두고 결과 요약표에 「보류(권장표 뒤 바뀜: {바뀐 것 — 상태 {현재 상태} / 상세 내용 / 선행 FR {slug} {이전}→{현재}})」 로 남깁니다. 표를 낸 뒤 다른 세션이 같은 FR 을 바꿨을 때 이전 판정이 최신 결정을 덮지 않게 하려는 것입니다. 다시 groom 하면 바뀐 근거로 새 권장을 냅니다.
- `parked` 로 정해진 행의 다시 볼 조건은 답에 적힌 조건, 없으면 권장표 근거 칸의 조건을 씁니다. 둘 다 없으면 그 행만 반영을 미루고 조건 한 문장을 묻습니다. 나머지 행은 먼저 반영합니다.

- 판정이 정해진 행은 5·6단계로 기록·반영합니다.
- 「따로」 를 고른 행은 「개별 문답」 절로 그 FR 만 다룹니다. 나머지 행의 반영을 먼저 끝냅니다.
- 「건너뛰기」 행은 기록·상태 변경 없이 `idea` 로 둡니다.
- 「중단」 이면 아직 반영하지 않은 행은 기록·상태 변경 없이 두고 결과 요약표를 보이고 끝냅니다. 이미 반영한 행은 그대로 둡니다.

### 5. 기록

상세 파일 끝에 아래 절을 덧붙입니다. `idea` 유지도 기록합니다(다음 groom 이 이어 갈 수 있게).

```markdown
## groom 기록 (YYYY-MM-DD)

- 판정: <validated | parked | dropped | idea 유지>
- 근거: <한두 문장. 확인한 파일·커밋·수치>
- 문답 요지: <질문과 정한 답을 한 줄씩. 권장표로 정했으면 그 사실과 사용자 답>
```

- 범위나 결정이 바뀌었으면 상세의 `request seed`·`related context` 도 고칩니다. `summary` 는 인덱스 요약 칸과 짝이라 바꾸지 않습니다.
- `dropped` 면 `rd-workflow/claude_skills/fr/status.md` 「규칙」 이 요구하는 세 가지(무엇이 왜 해결·무의미해졌는지, 폐기된 실측치·지표, 되살릴 조건)를 이 절에 적습니다.

### 6. 상태 반영

「판정 기준」 표의 반영 열대로 기존 절차를 따릅니다.

- `validated`·`dropped`: `rd-workflow/claude_skills/fr/status.md` 절차를 그대로 수행합니다.
- `parked`: `rd-workflow/claude_skills/fr/park.md` 절차를 그대로 수행합니다. 재평가 조건은 4단계(답 조건 → 권장표 조건 → 질문 순서) 또는 개별 문답에서 정한 문장을 쓰고, `park.md` 4단계에서 다시 묻지 않습니다.
- `idea` 유지: 상태를 바꾸지 않습니다.

### 7. 결과 요약표

끝나거나 중단하면 보입니다.

| FR | 결과 | 근거 |
| --- | --- | --- |
| `<slug>` | validated / parked(재평가: …) / dropped / idea 유지 / 건너뜀 / 중단 / 보류(사유) / 대상 아님(사유) | 한 줄 |

`/fr do` 가 부르지 않았고(사용자가 `/fr groom`·`/fr-groom` 을 입력함) groom 이 바꾼 파일이 있으면 표 아래에 「groom 결과는 커밋하지 않았습니다. `/fr do` 로 줄기를 띄우기 전에 아래 파일을 커밋하십시오 — 줄기는 기본 브랜치에 커밋된 상세를 받습니다」 와 파일 목록을 보입니다.

- 목록은 이번 호출이 5·6단계에서 직접 쓴 경로입니다. 반영하면서 경로를 적어 둡니다: 고친 상세 파일, 고친 인덱스 파일(`FUTURE_REQUESTS.md`·`FUTURE_REQUESTS_PARKED.md`), `status.md` 가 옮긴 raw capture 의 이동 전·후 파일 경로. 다른 세션이 그사이 바꾼 파일은 이 목록에 들어가지 않습니다.
- 이번 호출이 쓴 파일에 이번 호출 전의 미커밋 변경도 있으면(`git diff HEAD -- <파일>` 에 이번 호출이 쓰지 않은 줄이 보이면. stage 한 변경도 함께 봅니다) 그 파일을 「다른 변경과 섞임 — 커밋 전에 나눠 확인하십시오」 로 따로 적습니다.

## 개별 문답

사용자가 「N번 따로」(`N?`)를 고르거나 권장표로 결론이 나지 않는 FR 에 씁니다.

- 한 번에 한 질문만 합니다. 질문마다 권장 답과 그 근거를 함께 적습니다.
- 질문은 AskUserQuestion 질문 창으로 묻습니다. 첫째 선택지가 권장 답이고 라벨 끝에 「(Recommended)」 를 붙입니다. 선택지는 4개까지이고, 그 밖의 답은 「Other」 칸으로 받습니다.
- 질문 창을 쓸 수 없으면 선택지에 `1.` 부터 번호를 붙여 응답에 보이고 `1` 을 권장 답으로 둡니다. 사용자는 번호나 문장으로 답합니다. 선택지에 없는 번호이거나 읽을 수 없는 답이면 반영하지 않고 선택지를 다시 보이고 다시 묻습니다.
- 2단계에서 이미 확인한 사실은 다시 묻지 않고 근거로 씁니다. 앞 답이 결론을 정하면 남은 질문은 건너뜁니다.
- 마지막 질문은 판정입니다. 「판정 기준」 표의 결론 하나를 권장 답(첫째 선택지)으로 내고 근거를 한두 줄로 적습니다. 나머지 세 결론을 그 뒤 선택지로 둡니다. `parked` 를 골랐는데 다시 볼 조건이 없으면 4단계 규칙대로 조건 한 문장을 묻습니다.
- 결론이 나면 4단계 「반영 전 재확인」 을 거쳐 5·6단계로 반영합니다.
- 문장 답으로 이어 가면 뒤쪽 턴에는 frontmatter 의 `model`·`effort` 가 걸리지 않습니다(「모델·effort」 절).

## 규칙

- 사용자 명시 요청 전용입니다. 모델이 스스로 이 skill 을 시작하지 않습니다. `/fr groom` 입력, `/fr-groom` 입력, `/fr do` 대화형의 groom 질문에서 groom 을 고른 것이 명시 요청입니다.
- 사람이 답해야 하는 절차라 무인 실행(`/fr do --headless`, autopilot)에서는 돌리지 않습니다.
- 상태 변경 방식은 `status.md`·`park.md` 가 정본입니다. 이 skill 은 그 절차를 부를 뿐 인덱스·상세를 다른 방식으로 고치지 않습니다.
- 커밋은 하지 않습니다. `/fr status`·`/fr park` 와 같습니다. 대화형 `/fr do` 가 이 skill 을 불렀으면 결과 커밋은 `rd-workflow/claude_skills/fr/do.md` 「1. 고르기와 착수 보고 표」 4단계가 합니다.
